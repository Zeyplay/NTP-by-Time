## 1. Постановка задачи

### 1.1 Актуальность

Синхронизация времени является критически важной инфраструктурной задачей для:
- Корректной работы систем логирования и аудита безопасности
- Синхронизации распределенных баз данных и транзакций
- Работы протоколов безопасности (TLS, Kerberos, OAuth)
- Координации задач в кластерных и микросервисных средах

### 1.2 Цель проекта

Развернуть высокодоступный NTP-сервер на базе Chrony в контейнерной среде с соблюдением принципов Infrastructure as Code (IaC) и безопасности.

## 2. Анализ существующих решений

### 2.1 Сравнение NTP-серверов

| Критерий | Chrony | NTPd (ntpd) | OpenNTPD |
|----------|--------|-------------|----------|
| Скорость синхронизации | Высокая (секунды) | Низкая (минуты) | Средняя |
| Работа в изоляции | ✅ Отличная | ⚠️ Ограниченная | ✅ Хорошая |
| Поддержка NTS | ✅ Да | ✅ Да (новые версии) | ❌ Нет |
| Потребление ресурсов | Минимальное | Среднее | Минимальное |
| Активность разработки | ✅ Активная | ⚠️ Медленная | ⚠️ Медленная |

### 2.2 Обоснование выбора Chrony

**Chrony** выбран по следующим причинам:
1. **Быстрая синхронизация** — критично для виртуальных машин и контейнеров
2. **Режим изоляции** — отдача собственного времени при потере связи с интернетом
3. **Минимальный размер** — хорошо подходит для Alpine Linux контейнеров
4. **Современный стек** — активная разработка и поддержка NTS

## 4. Безопасность

### 4.1 Принцип наименьших привилегий

- Контейнер запускается от пользователя `chrony` (не root)
- Capability `SYS_TIME` добавлена только при необходимости
- Конфигурации монтируются в режиме read-only (`:ro`)

### 4.2 Изоляция

- Использование Alpine Linux (минимальная поверхность атаки)
- Изолированная Docker-сеть без доступа к default network
- Docker Secrets для передачи чувствительных данных

### 4.3 Контроль доступа

- Разрешены только локальные подсети (172.16.0.0/12, 10.0.0.0/8, 192.168.0.0/16)
- Запрещены все остальные подключения по умолчанию
